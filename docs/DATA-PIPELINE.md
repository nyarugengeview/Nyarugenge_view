# Nyarugenge data workflow

## Current design

The React/Vite application stays static-host friendly. `public/data/manifest.json` is the single runtime registry; `src/data/registry.ts` and `src/data/loaders.ts` read registered data. Only `verified` files are loaded into the map and category views. Discovery and processed review files live outside `public/data/`. User archives are read in place and never modified. GitHub Pages cannot accept uploads, so adding data means processing locally, reviewing it, committing approved outputs, and letting the Actions workflow publish the commit.

## Setup

Use Python 3.10 or later, with GDAL wheels provided by GeoPandas/Pyogrio. Install processing dependencies with `python -m pip install -r requirements-data.txt`. The NISR table extraction script additionally needs `pdfplumber` and `openpyxl` (included). Optional raster work requires Rasterio/GDAL and manual confirmation of the raster's location, CRS, control points, license, and coverage.

## Repeat the current acquisition and clipping run

The two supplied archives can be processed without copying them into the repository:

```powershell
python scripts/nyarugenge_data_pipeline.py `
  --archive "C:\path\to\DATASETS.zip" `
  --archive "C:\path\to\Data.zip"
```

For standalone vector inputs, use `--vector` once per source. For coordinate CSVs, also provide the documented CRS (for example `--csv-crs EPSG:4326`). For a public ArcGIS FeatureServer layer URL, use `--rest-layer`:

```powershell
python scripts/nyarugenge_data_pipeline.py --vector "data/input/facilities.gpkg"
python scripts/nyarugenge_data_pipeline.py --vector "data/input/facilities.csv" --csv-crs EPSG:4326
python scripts/nyarugenge_data_pipeline.py --rest-layer "https://host.example/server/rest/services/name/FeatureServer/0"
```

Or copy original archives to `data/input/` and use their relative paths. The script queries the public NISR village FeatureServer in pages, checks the Nyarugenge name and district ID `11`, dissolves the accessible NISR village polygons into district/sector/cell outputs, and clips vector Shapefiles in projected EPSG:32736 coordinates. Points are selected if covered by the boundary; lines and polygons are intersected with it. The output GeoJSON uses EPSG:4326. Existing outputs under `data/processed/pending-review/` are regenerated by deterministic filenames; original archives are untouched.

Outputs:

- The three NISR-derived boundary candidates are kept locally under `data/processed/pending-review/`; their manifest entries have status `pending-review` and no public file is bundled until vintage and reuse terms are confirmed.
- User archive clips are under `data/processed/pending-review/` and are not displayed publicly.
- `data/reports/data-inventory.json` records source counts, output counts, source CRS, output CRS, processing, validation and review notes.

The spatial script handles ZIP archives with Shapefiles, standalone GeoPackage/GeoJSON/Shapefile, coordinate CSV, and public ArcGIS FeatureServer layer URLs. REST reads are paged at 2,000 features per request, but features are assembled in memory before clipping; very large REST layers should be constrained to a relevant service query or processed with a streaming/batch adapter. For ZIP-contained File Geodatabases it inventories schema/extent and checks whether features intersect Nyarugenge; it does not convert or clip those GDB layers. GeoTIFF files are inventoried only; Rasterio clipping is not implemented. Do not treat an inventory-only record as a clipped output.

## Repeat the NISR population extraction

```powershell
python scripts/refresh_nisr_statistics.py
```

The script retrieves the official Nyarugenge 2022 and 2012 profile PDFs, 2023–2032 projection workbook, and Nyarugenge gender profile. It extracts the specified population tables, checks published totals against sex and sector sums, and verifies expected gender table rows and values. It writes normalized JSON and CSV under `public/data/statistics/` plus `data/reports/nisr-statistics-inventory.json`. If extraction or reconciliation fails, it stops rather than writing invented values. Inspect the source page/table references in each JSON and inventory record. Projection rows remain labelled as projections.

## Review and approve a new layer

1. Preserve the original archive in `data/input/` (or keep a durable external original), and record source URL, source organization, acquisition date, reference period, license, geographic coverage, and any restrictions.
2. Run the pipeline and inspect `data/reports/data-inventory.json`; confirm CRS against the source documentation, fields and source IDs, counts, geometry types, extent, clipping method, and validity. A district-name attribute filter only selects candidates; the geometric clip is separately recorded.
3. For supplied education layers, inspect for direct personal information (the current school file contains a headmaster field) and remove it only with a documented transformation and a lawful basis. For every source, resolve redistribution rights before bundling it in the static site.
4. Inspect output geometry and attributes in QGIS/ArcGIS Pro. Compare the output to `nyarugenge-district-nisr-derived.geojson`; look for slivers, unexpected extent, mismatched boundary vintage, and missing required fields. Have a data owner review it where a source or license remains ambiguous.
5. Only after approval, move or export the approved output under `public/data/geography/` or `public/data/facilities/`, add a complete manifest record with status `verified`, attribution, license, schema, reference period, geographic level, CRS, processing history and limitations. Never change status solely because processing succeeded.
6. Run data validation, tests, typecheck and production build. Confirm the layer, legend/attribution and popups in the map, and check the category's tables/charts. Verify mobile layout. Commit repository changes and push; GitHub Actions builds and publishes the static site.

## Checks and publish

```powershell
pnpm validate:data
pnpm test
pnpm typecheck
pnpm build
pnpm dev
```

The data report, app and original-source links contain access date and source details. The supplied archive does not include adequate item-level URLs, publication dates or license terms for its individual layers, so these outputs stay pending review. Its GADM 2.5 boundary files are explicitly non-commercial and redistribution requires consent; they are excluded from the public boundary layer. No source is considered verified only because it downloaded.

For static GitHub Pages publishing, commit approved processed files and manifest edits, push to the repository's configured branch, and allow `.github/workflows/deploy.yml` to complete. No app-side upload or backend exists or is needed for this commit-based workflow. Check the deployed manifest, homepage, map layer, source links and mobile layout after deployment.
